# Go-live readiness task board

Tracks what's pending before onboarding real customers at scale (discussed: ~1000 vendors,
hosted on Google Cloud Run). Update the status inline as items are picked up. Finished items are
removed from this board (the history is in git and in the regression notes).

Status values: `Pending`, `In Progress`, `Decision needed`, `Won't Fix` (with a one-line reason if so).

## 1. Shop listing: a shop must be activated before Super Admin can list it

Found 2026-10-19 by probing a live shop through every state. Three independent switches decide whether a
shop is public: the listing status (DRAFT / PENDING / LIVE), the account activation (`is_active`, the
"Reactivate Vendor" button) and the subscription status. Approving the listing does not check the other
two, so a shop whose documents have not been reviewed can go half-public: it is missing from the city
list but shows in browse-all, opens from its link and accepts orders, while its owner cannot sign in.
Activation is where the Super Admin review (GSTIN / documents) happens, so it has to come first.

## 2. High priority

| # | Task | Why it matters | Fix | Status |
|---|---|---|---|---|
| H1 | Razorpay webhook idempotency unverified | No confirmed guard against processing the same `payment_link.paid` event twice (Razorpay does retry webhook delivery). Cloud Run's auto-scaling (no `--max-instances` cap set, see H2) makes a retry landing on a second concurrent instance a real possibility, not just a theoretical one. See `backend/src/main/java/com/xerxes/msme/subscription/SubscriptionService.java` (`handleWebhookPaid`) and `RazorpayWebhookController.java`. | Add a dedupe check (for example a unique constraint or an "already processed" flag keyed on the payment link ID) before applying billing effects. | Pending |
| H2 | Public API rate limiter keeps its counters in one process's memory | `PublicApiRateLimiter` counters live in a single process. No `--max-instances` or concurrency flags are set in `scripts/deploy-backend.sh`, so Cloud Run will start several instances under real load. Each gets its own independent 30-requests-per-60-seconds budget, silently multiplying the real limit by the number of running instances, exactly when traffic (or abuse) is highest. | Move the counter to shared state (Memorystore/Redis, or a DB-backed counter), or deliberately cap `--max-instances` on the public-facing path as a stopgap. | Pending |
| H3 | Shopper search and area/pincode filters only cover the shops already loaded | The marketplace page loads 20 shops at a time (`PAGE_SIZE` in `MarketplacePage.tsx`, newest first) and filters them in the browser; the search text is not sent to the server. With about 1,000 vendors, a shopper searching for a shop by name gets "No shops found" if it is outside the 20 loaded (found 2026-10-19: a new shop fell off page 1 during a regression run and its search found nothing). | Send search, area and pincode to the public listings endpoint (`PublicMarketplaceService.listListingsPage`) so the server searches all shops, then drop the browser-side filter. Needs a breakdown into small steps first (backend query, API parameters, page wiring). | Pending |
| H4 | Subscription invoices do not add GST | The plan prices (Free ₹0, Plus ₹199, Premium ₹999 a month) are quoted without GST, but `SubscriptionService` invoices exactly the plan price with no GST line, so a vendor is billed less than the "plus GST" the pricing page will state. Decided 2026-10-27 to publish the prices as "plus GST". | Add GST to the subscription invoice amount and show it as its own line (rate to confirm; check how Razorpay payment links and invoice numbering will carry it), then match the pricing page. | Pending |
