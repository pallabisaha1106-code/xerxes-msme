# Xerxes MSME

Multi-tenant SaaS platform for MSME businesses to manage inventory (any product type) and GST billing.

## Structure

- `backend/` - Java 21 / Spring Boot 3, PostgreSQL, Flyway-managed schema
- `frontend-web/` - React + TypeScript + Vite web console (plain React + our own CSS design system, no UI library dependency)
- `frontend-mobile/` - React Native (Expo) mobile app (phase 2)
- `regression/` - Playwright end-to-end tests against the real stack

## Prerequisites

| Tool | Version | Notes |
|---|---|---|
| JDK | **21** | See [JDK note](#jdk-note-must-read) below - a newer default JDK will silently break the build |
| Maven | 3.9+ | `mvn -v` to check |
| Node.js | 18+ | `node -v` to check |
| Docker | any recent version | for local Postgres |

## Quick start (new machine, zero setup)

This brings up the whole stack in order: database → backend → frontend.

### 1. Start Postgres

```bash
docker run -d --name xerxes-msme-postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=xerxes_msme \
  -p 5432:5432 \
  postgres:16-alpine
```

This creates an empty `xerxes_msme` database. You do **not** need to manually run any
`.sql` file — the next step does that for you automatically.

Already have the container from before? Just start it again:
```bash
docker start xerxes-msme-postgres
```

### 2. Start the backend

<a id="jdk-note-must-read"></a>
**JDK note (must read):** the backend requires **JDK 21** to build. If your machine's
default JDK is newer (e.g. 25), Lombok's annotation processor doesn't support it yet and
getter/setter generation silently fails, producing confusing "cannot find symbol" compile
errors that have nothing to do with your code. Point `JAVA_HOME` at a JDK 21 install first:

```bash
export JAVA_HOME=/Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home   # adjust to your install path
```

Then run the backend:

```bash
cd backend
mvn spring-boot:run
```

On first boot, **Flyway automatically creates the entire schema** by running
`backend/src/main/resources/db/migration/V1__init_schema.sql` against the empty database
from step 1 — tables, indexes, constraints, everything. There's nothing to run by hand.
That file is also the canonical schema reference; its header comment explains the key
design decisions (multi-tenancy, the product/variant model, GST invoice numbering, the
stock ledger). Look for a line like this in the logs to confirm it worked:

```
Successfully applied 1 migration to schema "public", now at version v1
```

The backend is now up on `http://localhost:8080`, connected to Postgres using the
built-in defaults (`localhost:5432`, db `xerxes_msme`, user/password `postgres`/`postgres`
— see [Configuration](#configuration-env-vars) to override any of these).

### 3. Start the frontend

In a new terminal:

```bash
cd frontend-web
npm install
npm run dev
```

Open **http://localhost:5173**. Click **Register** and create your own business account
— there's no seeded login. Registering creates both the business (tenant) and you as its
`OWNER` in one step; use that email/password to log in from then on.

That's the whole stack running locally.

## Running the tests

### Backend unit/integration tests

```bash
cd backend
mvn verify
```

`mvn verify` runs the full test suite and then a JaCoCo coverage gate: the build **fails**
if line coverage across the module drops below 85% (`jacoco.coverage.minimum` in `pom.xml`).
Entity/DTO boilerplate generated by Lombok is excluded automatically; everything else
(services, controllers, security, GST/stock calculations) is expected to carry real tests.

### End-to-end tests (Playwright)

See [regression/README.md](regression/README.md) for full details. Short version:

```bash
cd regression
npm install
npx playwright install --with-deps chromium   # first time only
npm test
```

These drive a real browser against the backend/frontend/database you started above, so
they need to already be running. There's also a standing test account
(`veera@test.com` / `password1234`) documented there for any test that needs to be
logged in as an existing user rather than registering a fresh one.

## Configuration (env vars)

All of these have working defaults for local dev (matching the Docker setup above) — you
only need to set them for a non-default setup (different port, different DB name, a real
JWT secret in a deployed environment, etc).

| Variable | Default | Used for |
|---|---|---|
| `DB_HOST` | `localhost` | Postgres host |
| `DB_PORT` | `5432` | Postgres port |
| `DB_NAME` | `xerxes_msme` | Postgres database name |
| `DB_USER` | `postgres` | Postgres user |
| `DB_PASSWORD` | `postgres` | Postgres password |
| `SERVER_PORT` | `8080` | Backend HTTP port |
| `JWT_SECRET` | a placeholder, **not safe for production** | Signs auth tokens - set a real secret outside local dev |
| `JWT_EXPIRATION_MINUTES` | `60` | How long a login session's token stays valid |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173` | Comma-separated list of origins allowed to call the API from a browser |

Full list with descriptions: [backend/src/main/resources/application.yml](backend/src/main/resources/application.yml).

## Troubleshooting

- **`cannot find symbol` errors mentioning getters/setters that clearly exist in the code**
  → you're building with a JDK newer than 21. See the [JDK note](#jdk-note-must-read) above.
- **Backend fails to start with "Port 8080 was already in use"**
  → something else is already running (maybe a previous `mvn spring-boot:run` you forgot
  about). Find and stop it: `lsof -ti:8080 | xargs kill`.
- **Frontend calls to the API fail with a CORS error in the browser console**
  → only happens if you're running the frontend on a port other than 5173, or calling the
  backend directly instead of through Vite's dev proxy. Add your frontend's origin to
  `CORS_ALLOWED_ORIGINS` (see [Configuration](#configuration-env-vars)).
- **Flyway complains about a checksum mismatch on `V1__init_schema.sql`**
  → you edited an already-applied migration file. Never edit a migration once it's been
  run against a real database; add a new `V2__...sql` file instead. For a throwaway local
  DB, easiest fix is to drop and recreate the container (step 1) so it re-applies cleanly.
